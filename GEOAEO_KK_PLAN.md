# GEOAEO_KK_PLAN — план индексируемой казахской версии `/kk/`

Статус: **план, не внедрено.** Внедрение требует согласования языковой архитектуры и перевода контента носителем языка.

## 1. Текущее состояние

- Казахский доступен только через переключатель `LangToggle` (`src/lib/lang-context.tsx`, значение в `localStorage`).
- URL не меняются, `<html lang="ru">` на всех страницах, сервер отдаёт только русский.
- Поисковики и AI-краулеры не видят казахскую версию. Hreflang не добавлен, так как эквивалентных URL нет.
- Переведено в `translations.ts`: интерфейс, главная, услуги (верхний уровень). **Не переведено:** статьи блога (17), `services-data.ts` (тексты, FAQ, SEO-поля), глоссарий, кейсы (`src/data/cases.ts`), юридические страницы, JSON-LD, llms.txt.

## 2. Варианты архитектуры

**A. Сегмент `[lang]` в App Router (рекомендуется).** `src/app/[lang]/...` с `ru` (по умолчанию без префикса) и `kk` (`/kk/...`).
- Плюсы: один код, единые шаблоны, hreflang и canonical формируются в `generateMetadata`.
- Минусы: перенос всех маршрутов; `ru` без префикса требует rewrite в `next.config.ts` или отдельной группы маршрутов.

**B. Отдельные маршруты `src/app/kk/...`.** Дублирование страниц.
- Плюсы: изоляция. Минусы: дублирование кода, расхождения, сложнее поддерживать.

Рекомендация: **A**, с `ru` без префикса (текущие URL не меняются).

## 3. SEO-требования для внедрения

- `<html lang>` = `ru` или `kk` по сегменту.
- Self-referencing canonical на каждой языковой версии.
- `alternates.languages`: `ru` ↔ `kk`, плюс `x-default` = `ru`. Только для реально существующих пар URL.
- Title и Description уникальны на каждом языке.
- Sitemap: отдельные записи для `/kk/...` с `xhtml:link` alternates.
- JSON-LD `inLanguage` = `kk` в казахских версиях статей и страниц.
- Переключатель языка — обычные `<a href>` на соответствующий URL (сейчас это `localStorage`).
- llms.txt: раздел для казахской версии, если она появится.

## 4. Объём контента

| Группа | Объём | Что нужно |
|---|---|---|
| Интерфейс и главная | уже переведено частично | проверить полноту, убрать RU-заглушки |

## 5. Риски

- Машинный перевод без проверки даёт некорректные юридические формулировки и SEO-тексты. Нужна вычитка носителем.
- Перенос маршрутов в `[lang]` меняет структуру, но не URL `ru`. Нужно проверить редиректы и sitemap до деплоя.
- Пока `ru` и `kk` не переведены полностью, казахская версия не должна попасть в sitemap (иначе это тонкий контент).

## 6. Решения, которые нужны от владельца

1. Вариант A или B (рекомендуется A).
2. Объём: полная казахская версия или только главная, услуги и 3–5 статей на первом этапе.
3. Кто переводит и вычитывает: носитель казахского, желательно с опытом в маркетинге.
4. Юридическое название компании и текст политики/условий на казахском.
5. Нужен ли `/kk/` до или после первого замера AI-видимости.

## 7. Порядок работ после согласования

1. Перенос маршрутов в `[lang]` без изменения контента, тесты: все 33 URL отдают 200 и тот же HTML для `ru`.
2. Подключение `kk`-словарей и `generateMetadata` с alternates.
3. Перевод по приоритету (услуги → главная → статьи).
4. Sitemap и llms.txt.
5. Строгий аудит (`seo:audit --strict`) для обоих языков, проверка hreflang на парность.

## 8. Окончательная рекомендация по архитектуре (2026-11-03)

Важное уточнение к разделу 2. Оба варианта требуют **переноса корневого layout**. Сейчас `<html lang="ru">` задан в `src/app/layout.tsx` один раз, а вложенный layout не может поменять атрибут `lang` у `<html>`. Поэтому языковой атрибут нельзя задать только добавлением маршрутов.

**Вариант A — `[lang]` с внутренним rewrite (рекомендуется).**
- `src/app/[lang]/layout.tsx` рендерит `<html lang={lang}>`; страницы переезжают в `[lang]` без изменения содержимого.
- Публичные `ru` URL не меняются: `next.config.ts` переписывает `/x` во внутренний `/ru/x`, `/kk/x` остаётся как есть. Это проверяемо: сравниваем HTML 33 `ru`-страниц до и после.
- Один код шаблонов, hreflang и canonical формируются из одного места.
- Риск: большой одноразовый diff. Снижается тем, что перенос делается без изменения контента и проверяется сравнением HTML.

**Вариант B — отдельное дерево `app/kk/` с route groups `(ru)` и `(kk)`.**
- Требует переноса существующих страниц в группу `(ru)` (URL не меняются) и дублирования маршрутов `kk`.
- Меньше изменений в уже работающих `ru`-страницах на этапе переноса, но постоянное дублирование и два места для правок. Каждое изменение дизайна или SEO-разметки придётся делать дважды.

**Итог:** A, но только после согласования и первым шагом — перенос без изменения контента, с проверкой 33 HTML-страниц до и после. Если владелец не хочет структурных изменений `ru`-части, допустим B как временный вариант на 3–5 страниц, с понятием, что поддержка удвоится.

**Что не делаем без согласования:** массовую миграцию маршрутов, переименование URL `ru`, любые изменения в production-настройках.

## 9. План первой казахской версии (после согласования)

**Состав (минимум, рекомендуется):**
1. Главная `/kk`.
2. Услуги: `/kk/services` и страница GEO/AEO `/kk/services/geo-aeo-optimizaciya`.
3. Ключевые услуги: SEO, AI-автоматизация (2 страницы из 5 — остальные после первой вычитки).
4. 3–5 статей блога, выбранных по трафику или по роли в воронке (например, «Что такое GEO-оптимизация», «Что такое AEO-оптимизация», «Как выбрать GEO/AEO-агентство»).
5. Не переводим: кейсы (до появления подтверждённых), иллюстративные примеры, глоссарий (второй этап).

**Требования к переводу:**
- Перевод выполняет носитель казахского, желательно с опытом в маркетинге. Машинный перевод публикуется только после вычитки.
- Глоссарий терминов, согласованный с владельцем: GEO, AEO, SEO, Schema.org, llms.txt — латиницей с пояснением при первом упоминании.
- Цифры, цены и даты переносятся из `ru`-версии без изменений; любые изменения согласовываются.
- Казахская версия не должна содержать утверждений, которых нет в `ru` (проверяется сверкой с реестром `GEOAEO_CLAIMS_REGISTRY.md`).
- Иллюстративные примеры переводятся с пометкой «иллюстративный».

**Юридические страницы:**
- `/kk/privacy` и `/kk/terms` публикуются **только** после перевода юристом и подтверждения юридического названия компании. До этого в казахской версии ссылки на юридические страницы ведут на `ru`-версию, а их пары в hreflang не объявляются.

**Canonical:**
- Каждая языковая страница имеет self-referencing canonical на собственный URL (`/kk/...` для казахской).
- Canonical не указывает с казахской страницы на русскую.

**Hreflang:**
- Объявляется только для реально существующих пар: `ru` ↔ `kk` и `x-default` → `ru`.
- Для страниц без казахского аналога hreflang не добавляется.
- Проверка: каждая пара должна ссылаться в обе стороны; ошибка парности — P1 в строгом аудите.

**Sitemap:**
- В sitemap попадают только опубликованные `kk`-URL.
- Для каждой пары — `xhtml:link rel="alternate" hreflang` с обеими версиями.
- Страницы без перевода в sitemap для `kk` не добавляются (тонкий контент).

**Прочее:**
- `<html lang="kk">` на казахских страницах; `inLanguage: "kk"` в JSON-LD.
- Переключатель языка — обычные ссылки на пару URL, а не `localStorage`.
- Строгий аудит расширяется на `kk`: проверка hreflang-парности, `lang`, canonical.

**Критерии готовности первой версии:** все `kk`-URL отдают 200; `ru`-HTML не изменился (сравнение с базой); строгий аудит проходит для обоих языков; вычитка переводов подтверждена владельцем; sitemap и hreflang проверены на парность.

**Что остаётся вне этой версии:** полный перевод блога, глоссария, кейсов, llms.txt-раздела на казахском, нативных казахских страниц для услуг вне списка.
